# Japan Rule 観光商品・有料化実装計画

## 判断

有料化へ進められる。初回は海外法人・事業者向けの「日本法一次資料と画面実装チェックの定型パック」に限定する。

個別案件について「適法」「登録不要」「法令が適用されない」と断定する機能は実装しない。旅行予約、宿泊手配、取消、代金収納にも関与しない。

## 最小商品

- 対象: 日本向けホテル予約・紹介サービスを運営する海外法人・事業者
- ケース: A=紹介リンク、B=自社予約・現地払い、C=自社予約・事前決済
- 無料部分: 入力検証、ケース分類、入力不足項目の提示、商品説明
- 有料部分: 一次資料、根拠位置、一般要件、画面チェックリスト、未確認事項、再確認トリガーをJSONで提供
- 仮価格: 1ケースUSD 25。海外法人向けの市場検証用であり確定価格ではない
- 対象外: 法的助言、適法性判定、登録要否の断定、規約の個別作成、民泊、旅行手配、旅行代金決済

## 出力仕様の修正

現在の `applicable / not_applicable` は法的結論と受け取られる可能性があるため、次の情報提供型スキーマへ変更する。

- `service_flow_type`: A / B / Cという事実上のサービス類型
- `observed_facts`: 入力から機械的に確認できた事実
- `missing_facts`: 判定材料として不足している事実
- `general_requirements`: 類型に関連する一般要件
- `official_sources`: 資料名、URL、根拠位置、確認日、版、ハッシュ
- `screen_checklist`: 画面に存在するか確認する項目
- `change_triggers`: 再確認が必要になる仕様変更
- `professional_review_triggers`: 弁護士・行政への確認を促す条件
- `information_only`: 常に `true`

禁止する出力は `compliant`、`legal`、`registration_not_required`、`no_legal_risk` などの個別法的結論。

## 実装順

1. 商品境界をコードと文言に固定する。対象、対象外、禁止出力、利用者を海外事業者に限定する。
2. A/B/C分類器を決定的ルールで実装する。入力不足・矛盾時は `needs_input` または `manual_review` で課金前停止する。
3. 観光ルールパックを追加する。根拠本文、資料URL、確認日、版、ハッシュを固定データとして管理する。
4. JSONスキーマとテストを追加する。禁止語、必須根拠、入力不足停止、A/B/Cの代表ケースを確認する。
5. 無料preflightと有料取得を分離する。支払いは入力ハッシュ、ルール版、価格、receiptに結合し、同じ支払いの再利用を拒否する。
6. 販売表示を準備する。提供内容、価格、支払時期、提供時期、取消・返金条件、事業者情報、利用規約、プライバシー表示を整える。
7. ログを最小化する。旅行者名、予約番号、旅券、決済情報、健康情報の入力を禁止し、保存期間と削除方法を定める。
8. ステージングで購入前後を通し確認する。入力不足では請求されず、正常時だけ同一内容の成果物が再取得できることを確認する。
9. 入出力例と販売文言を日本の弁護士へ一度確認に出す。必要なら経産省のグレーゾーン解消制度も検討する。
10. 明示承認後に限定公開し、B/C対象者へ有料テストを行う。

## 完了条件

- 3ケースが同じ入力から常に同じ類型・根拠を返す
- 入力不足・矛盾時に課金されない
- すべての有料出力に一次資料、根拠位置、確認日、版がある
- 個別の適法性・登録要否を断定しない
- 旅行者の機微情報を受け付けない
- 支払いの二重利用、異なる入力への流用、異なる価格への流用を拒否する
- 販売表示、規約、プライバシー表示が確認済み
- 法務確認で販売文言と出力境界が許容される
- ステージングの購入・再取得・失敗経路が通る

## 工数と進行判断

- ローカルMVP: 3〜5人日
- 決済・販売表示・ステージング確認: 1〜2人日
- 合計概算: 4〜7人日。法務確認の待ち時間、公開、本番課金運用は含まない

ローカル実装は開始可能。外部公開、デプロイ、本番課金、実顧客への案内は、それぞれ明示承認後に行う。

## 最初の販売検証

- 仮価格: USD 25
- 最小目標: 30日で3件、売上USD 75以上
- 継続条件: 購入者が定型出力だけで価値を得られ、個別の人手法務対応が常態化しない
- 見直し条件: 適格閲覧20件または購入導線開始10件で購入ゼロ
- 見直し時の対応: 機能追加を先行せず、顧客像、訴求、価格の順に再検討する
